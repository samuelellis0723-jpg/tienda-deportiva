# Decisiones del rediseño

1. **Proyecto local.** Se conserva React 18/Vite/Router, API Express y PostgreSQL como fuente de verdad. No hay publicación, commits, cambios de esquema, backend o workflow.
2. **Estado previo.** `git status --short` mostró únicamente `documentacion-ia/Bpracticas.md` y `documentacion-ia/reglas.md` sin seguimiento; no había cambios staged. Ambos se leyeron y permanecen intactos.
3. **Nomenclatura.** Las dos guías nuevas discrepan sobre PascalCase/kebab-case de archivos. Se conserva la convención efectiva PascalCase para componentes y kebab-case para servicios/utilidades, sin renombrar el proyecto.
4. **Marca y medios.** Se adapta la dirección sobria existente. Hero SVG original de un gi; no requiere dependencia, generación de bitmap ni descarga externa. Los colores propios de la ilustración representan tejido/sombra, no estados interactivos. El resto de la UI usa tokens compartidos.
5. **API primero.** No se amplían categorías, capacidades, endpoints o políticas. La API solo ofrece una `imageUrl`: galería con zoom de esa imagen sin miniaturas duplicadas para fingir ángulos. No existe endpoint de colecciones en el router real; se presenta lo más reciente y se etiqueta así, sin fingir colecciones destacadas.
6. **Envío.** Se conserva el flujo existente por n8n. Header consulta ciudades y cotiza subtotal cero para obtener `freeShippingThreshold`. Si la consulta falla muestra información de cobertura sin prometer un umbral. Carrito estima; checkout consulta nuevamente y Express revalida.
7. **Pago y reintentos.** Pago manual, sin pasarela. El intento idempotente y resultado viven en OrderContext durante la sesión de la aplicación, incluso al cambiar de ruta. Mientras se envía o hay resultado incierto, se bloquea la edición del carrito. Un error de red/5xx conserva payload y clave para reintento idéntico; un rechazo definitivo 4xx libera el intento. No se persiste información de contacto en almacenamiento. Se advierte al intentar cerrar/recargar con un intento pendiente. La recuperación después de una recarga forzada no está implementada.
8. **Panel.** Despublicar varios productos usa endpoints existentes, confirma antes de actuar y explica resultados parciales. Orden de tabla limitado a la página actual se etiqueta. Productos usa paginación servidor; cupones pagina el listado recibido.
9. **Contenido incompleto de negocio.** No hay contacto, redes oficiales, tabla de centímetros por modelo ni política de cambios proporcionados. Se omiten enlaces falsos y promesas; ayuda explica únicamente lo comprobable. Estas ausencias requieren contenido real del negocio para una entrega comercial definitiva.
10. **Dependencias.** No se agregaron paquetes. Rutas con lazy/Suspense separan pantallas. Se agregó `scripts/dev.mjs` porque el bundling automático de `vite.config.js` fallaba por acceso a directorios superiores en el sandbox; importa la misma configuración por ESM y mantiene proxies. Tests SSR desactivan WebSocket para no competir con preview.
11. **Límites de verificación.** Existe API local accesible y el webhook devuelve ciudades/cotización; no se crean órdenes ni se confirma pago contra datos reales. No se afirma despliegue de migraciones, integración PostgreSQL completa ni funcionamiento de IA en producción. Sin navegador conectado no se aprueba verificación visual o Lighthouse.
12. **Deporte y tipo de catálogo.** Se reutilizan `categories.parent_id` y `product_categories`, ya jerárquicas y many-to-many. `judo`/`bjj` son raíces canónicas; categorías hijas son tipos. Los filtros de API `deporte` y `tipo` son aditivos; una subconsulta `EXISTS` evita duplicados. No se añade tabla o columna ni se cambia checkout.
13. **Clasificación histórica.** No se adivina disciplina o tipo a partir del nombre. Admin muestra «Sin asignar»; tienda usa «Deporte por confirmar». Ediciones que no tocan la clasificación dejan asociaciones intactas; altas y reemplazos explícitos de categorías exigen deporte(s) y un tipo.
14. **Semilla comercial.** Se agregan categorías para rashguard y cinturón BJJ porque ya hay productos de esos tipos en la semilla; no se añaden productos, medidas, claims ni líneas no-gi o accesorios no presentes. La semilla no se ejecuta automáticamente ni contra la base conectada.
15. **Catálogo común.** `005_product_type_taxonomy.sql` crea/mapea seis categorías bajo `uniformes` en bases existentes con datos, sin cambiar estructura SQL. Conserva etiquetas Judo/BJJ, no reactiva categorías desactivadas al repetir la migración y solo preserva BJJ para cinturones que antes eran hijo de BJJ. El seed crea inventario de demostración y no sustituye el paso de migración en producción.
16. **Medios propios.** Se bloquean imágenes remotas de terceros en escritura y presentación. Las ilustraciones y fotografías autorizadas se sirven desde `/catalog-art/` del mismo sitio; los cinturones usan una ilustración de fallback coherente con el color de variante.
